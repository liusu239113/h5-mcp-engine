# 验收与试玩 —— **H5 工程专用**（改完必须自己玩一遍，别等用户找 bug）

> 🔴 **先确认工程类型。** 这份只适用于 **H5 工程**（根目录有 `index.html`，
> 没有 `scripts/main.lua` / `urhox-libs/`）。
>
> **Maker / UrhoX 工程不要用这份** —— 它的验证流程完全不同（你截不到图，
> 只能靠 `maker_build_current_directory` 构建 + 请用户看预览页）。
> Maker 走 `maker-handbook.md` 第 3 节。

适用：**每一次**改动 H5 游戏逻辑之后。

这是本引擎里最容易被跳过、也最影响交付质量的一步。
用户的原话是：「他老是不喜欢去验证游戏逻辑有没有问题，既不会跑测试脚本，也不会自己去玩，
导致游戏其实会出现很多 bug。」

**所以这条是硬要求，不是建议：没跑过下面这套流程，不许说「完成」。**

---

## 0. 三层验证，一层都不能省

```
第 1 层 · 静态自检   game_validate            → 有没有报错
第 2 层 · 逻辑自测   js_eval 跑断言脚本        → 逻辑对不对
第 3 层 · 自动试玩   tap / swipe 真玩 + 截图   → 玩起来对不对
```

很多人只做了第 1 层就说「没问题」—— 但**游戏最大的 bug 是「能跑通、但玩不了」**：
按钮点不动、碰撞不触发、分数不涨、死了不能重开。
这些 `game_validate` 一个都发现不了，**只有第 2、3 层能发现**。

---

## 1. 第 1 层：静态自检

```
game_validate
```

它会重载、跑一会儿、把 console 报错和页面状态给你。
有报错 → 先修，别往下走。

⚠️ 「没有报错」≠「功能正常」。继续第 2、3 层。

---

## 2. 第 2 层：逻辑自测（跑断言脚本）

用 `js_eval` 直接驱动游戏状态，断言结果。**这是找逻辑 bug 最有效的一招。**

### 关键：把游戏状态暴露出来

游戏代码里要留一个调试入口（交付前可保留，代价极小、收益极大）：

```js
// game.js 末尾
window.__G = G;          // 游戏状态对象
window.__api = {         // 需要被测试的操作
  start: startGame,
  move: movePlayer,
  spawn: spawnEnemy,
  reset: resetGame
};
```

### 然后写断言脚本

```js
// js_eval 跑这段
(function(){
  const G = window.__G, api = window.__api;
  const fail = [];
  const ok = (cond, msg) => { if (!cond) fail.push(msg); };

  // ---- 用例 1：初始状态 ----
  ok(G.score === 0, '初始分数不是 0，实际 ' + G.score);
  ok(G.lives === 3, '初始命数不是 3，实际 ' + G.lives);
  ok(G.state === 'ready', '初始状态不是 ready，实际 ' + G.state);

  // ---- 用例 2：开始游戏 ----
  api.start();
  ok(G.state === 'playing', 'start 之后状态不是 playing，实际 ' + G.state);

  // ---- 用例 3：得分 ----
  const before = G.score;
  api.move(10);                       // 直接驱动，不依赖真实按键
  ok(G.score > before, '得分没涨：' + before + ' → ' + G.score);

  // ---- 用例 4：碰撞 ----
  G.player.y = G.enemies[0].y;         // 强行造出碰撞条件
  G.player.x = G.enemies[0].x;
  tick(1/60);                          // 手动推进一帧
  ok(G.lives === 2, '碰撞没扣命，实际 ' + G.lives);

  // ---- 用例 5：死亡与重开 ----
  G.lives = 0;
  tick(1/60);
  ok(G.state === 'over', '命没了没进结算，实际 ' + G.state);
  api.reset();
  ok(G.state === 'ready' && G.score === 0, '重开没复位');

  return fail.length ? ('❌ 失败 ' + fail.length + ' 项:\n' + fail.join('\n'))
                     : '✅ 全部 ' + 5 + ' 组用例通过';
})()
```

### 要点

- **每个断言都要带上实际值**（`'实际 ' + G.score`）——
  只回「失败」等于没说，你还得再跑一次才知道差在哪。
- **一次把用例写全**再跑，别一条一条来（每次 `js_eval` 都是一个来回）。
- 边界一定要测：**0、负数、最大值、空数组、连点两次**。
- 游戏的**核心循环**必须有用例：开始 → 得分 → 失败 → 结算 → 重开。
- 拿不到 `window.__G` 时：先 `game_read` 看游戏把状态放在哪个变量里，
  用 `js_eval` 读 `Object.keys(window)` 找。

## 3. 第 3 层：自动试玩（真的去玩）

逻辑对了不代表玩得爽、点得动。**要用 `tap` / `swipe` 真的操作一遍。**

### 标准流程

```
1. game_shot                     → 看开始界面长什么样，记下按钮位置
2. tap(x, y, space="shot")       → 点「开始」（坐标直接从截图量，不用换算）
3. game_shot                     → 确认真的进了游戏（不是没反应）
4. tap / swipe 做几个核心操作
5. game_shot                     → 确认状态真的变了（分数涨了？角色动了？）
6. game_shot_motion              → 判断「动得对不对」（方向、轨迹、动画）
7. 玩到失败 → 截图
8. tap 重开 → 截图确认回到开始
9. console_logs                  → 全程有没有报错
```

### 坐标怎么取（这一步最容易做错）

**推荐用 `space="shot"`**：直接用在 `game_shot` 图上量到的像素坐标。
少一次换算，也不会算错。

```
game_shot → 看图，按钮大概在 (180, 520)（图上的像素）
tap(x=180, y=520, space="shot")
```

⚠️ 不要凭「设计稿坐标」猜。设计尺寸和实际渲染尺寸不一样。

### 动得对不对，用 game_shot_motion

旋转方向反了、动画卡住、抛物线不自然 —— 这些**单帧看不出来**。

```
game_shot_motion(frames=6, interval_ms=120)
```

它连抓多帧拼成一张网格图，看轨迹是不是闭合、方向对不对、有没有跳帧。

### 要可复现，用 setup 冻结状态

```
game_shot_motion(frames=6, setup="G.player.x = 100; G.player.vy = -8;")
```

`setup` 会在每一帧前跑一次，`i` 是帧序号 —— 这样「第几帧是什么样」是确定的，
不依赖真实渲染速度，能稳定复现。

## 3.5 试玩期间**不要写文件**（这条能解释一半的「玄学 bug」）

`game_write` / `game_patch` 会**自动热重载**页面 —— 这是引擎的设计行为，
不是「有人在外部改你的文件」。

所以：

- **先把代码改完，再去试玩。** 试玩到一半又去 `game_write`，页面会被重载，
  你刚玩到的进度、刚建立的状态**全没了**，你会看到「游戏自己回到了主菜单」。
- 真遇到「页面自己刷新了 / 状态自己回退了」→ **先调 `file_journal`**，
  它会告诉你最近是谁、什么时候、写了哪个文件、触发了什么重载。
  流水里那条 `auto-reload` 就是你自己刚才那次写入引起的。
- 流水是空的 → 没有文件被改，问题在**页面自身逻辑**（定时器 / 状态机 / 音频策略），
  去读代码，别去猜外部进程。

> ⚠️ 本 App **没有**文件监听器、没有后台同步、没有外部进程会改工程文件。
> 会写文件的只有三个来源：
> 1. **你自己**（主线的 `game_write` / `game_patch` / `game_create`）；
> 2. **你派出去的子任务**（`subtask` 的助手，和你共用同一套工具）；
> 3. 用户在 App 里手改保存。
>
> 第 2 条最容易漏：**子任务写文件一样会热重载**，一样会把你的预览冲回主菜单。
> 如果你正在等子任务、同时又发现「预览自己跳回主菜单了」——那就是它在写，不是外人。
>
> **不要**在给用户的结论里写「有外部进程 / 另一个 AI 在动文件」——那是误判，
> 用户会以为你在推卸责任。

## 4. 玩的时候重点找这几类 bug

| 类型 | 怎么发现 |
|---|---|
| **点不动** | tap 之后 `game_shot`，画面没变 = 按钮没接上 / 被遮挡 / 热区太小 |
| **热区太小** | tap 在按钮边缘失败 → 触摸目标要 ≥ 44px |
| **卡死** | 玩到某个状态后任何操作都没反应（缺了「失败后能重开」的出口） |
| **数值错** | 用 js_eval 断言分数 / 血量 / 关卡的变化量 |
| **边界崩** | 分数为 0 时重开、连续点两次开始、通关后再玩 |
| **视觉错位** | game_shot 看有没有出屏、重叠、被系统栏压住 |
| **动得不对** | game_shot_motion 看方向 / 轨迹 / 跳帧 |
| **性能掉帧** | js_eval 测平均帧耗时（见下） |
| **静默失败** | 操作了但没反馈（没有音效 / 飘字 / 动画）—— 用户以为没点到 |

### 性能实测（别凭感觉）

```js
// js_eval
(function(){
  let n = 0, t0 = performance.now();
  return new Promise(r => {
    function f(){ if (++n >= 120) r('平均帧 ' + ((performance.now()-t0)/n).toFixed(2) + 'ms');
                  else requestAnimationFrame(f); }
    requestAnimationFrame(f);
  });
})()
```

> 16.7ms ≈ 60fps。超过 20ms 就要查（多半是每帧 new 对象或每帧重绘背景）。

## 5. 验收清单（每条都要有证据）

交付前逐条过，**每条都要能说出「我怎么验的」**：

- [ ] `game_validate` 跑过，**零报错**
- [ ] `js_eval` 断言脚本跑过，**核心循环全部通过**（开始/得分/失败/结算/重开）
- [ ] `tap` 点过开始按钮，**截图确认真的进了游戏**
- [ ] 做过至少 3 个核心操作（移动 / 射击 / 跳跃 / 翻页），**每次截图确认状态变了**
- [ ] 玩到失败，**截图确认结算页正常**
- [ ] 点重开，**截图确认回到开始**（不是卡死）
- [ ] 边界测过：0 分重开、连点两次、空状态
- [ ] `game_shot_motion` 看过关键动作的方向 / 轨迹
- [ ] 帧耗时实测过（< 20ms）
- [ ] 全程 `console_logs` 无报错

**缺任何一条 → 还没做完。**

## 6. 汇报格式（用户要看到证据，不是「已完成」）

```
改了什么：<一句话>
怎么验的：
  · game_validate → 零报错
  · 断言 5 组全过（开始/得分/碰撞/结算/重开）
  · 实际玩了一遍：点开始 → 得 12 分 → 撞敌人 → 结算 → 重开，都正常
  · 帧耗时 8.2ms
还剩什么：<如实说，没有就写「无」>
```

❌ **不许**只说「已修复 / 已完成 / 没问题了」。没有验证过程的说辞，用户不信也不该信。

## 7. 最容易犯的五个错

| 错 | 后果 |
|---|---|
| 只跑 `game_validate` 就宣布完成 | 能跑通但玩不了的 bug 全漏掉 |
| 用「设计稿坐标」猜 tap 位置 | 点不中，然后误判成「按钮坏了」 |
| 只截一张图就下结论 | 运动类问题单帧看不出 |
| 断言只回「失败」不带实际值 | 你还得再跑一次才知道差在哪 |
| 没测「失败后重开」 | 游戏卡死，这是最影响体验的 bug |
