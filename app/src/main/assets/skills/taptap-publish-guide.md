# TapTap 发布手册（素材 / 上传 / 提审）

发布页在 App 的「发布」标签里。这份讲**怎么用**它、以及背后的规矩。

---

## 一、核心模型：发布页是「预览台」，不是「上传按钮」

```
① 本地准备阶段          ② 一键发布
   ┌─────────────┐         ┌──────────────────────┐
   │ icon      ✅│  点      │ 传素材 → 写字段        │
   │ 截图      ✅│ ──────→  │ → 复查 → 快照 → 预检   │
   │ 横版封面  ⬜│ 「我要   │ → 用户确认 → 提审      │
   │ 宣传图    ⬜│  发布」  └──────────────────────┘
   └─────────────┘
```

**先把素材在本地备齐、看清楚了，再一次性推上去。**

不是「点一下传一张、传到哪不知道」—— 那样用户既看不到齐不齐，
也不知道传上去之后商店页会变成什么样。

---

## 二、素材是**按字段**管的，不是一个「素材库」

TapTap 商店页的每个位置是**独立字段**，各有一套规格：

| 字段 | 是什么 | 比例 | 最小尺寸 | 大小上限 |
|---|---|---|---|---|
| `icon` | 游戏图标 | 1:1 | 512×512 | — |
| `screenshots` | 游戏截图（可多张） | 竖屏常见 3:8~5:8 | 720×1280 | — |
| `banner_4` | 横版宣传主图 | 16:9 | 1920×1080 | **4 MB** |
| `square_promo_image` | 方形宣传图 | 1:1 | — | — |
| `trailer` | 宣传视频 | — | — | — |
| `gameplay_demo_video` | 玩法演示 | — | — | — |

⚠️ **规格以 `get-app-module` 当次返回的 `image_spec` / `video_spec` 为准**，
上面这张表只是常见值 —— 官方会按平台/游戏类型调整。

**`icon` 有个坑**：`contentNote` 写着「不要预加圆角」，商店会自己加圆角。
你传一张已经带圆角的图，显示出来就是**双层圆角**。

---

## 三、上传 ≠ 完成（最容易搞错的一步）

官方原话：**「上传成功不等于资料字段已写入，也不等于资料页包体已绑定。」**

正确流程是**两步**：

```
① upload <图片>              → 收进素材库，返回 https URL
② save-changes               → 用这个 URL 写进具体字段
     {field_id, op, value, expected}
```

**只做 ① 的话，图只是躺在素材库里，商店页上什么都看不到。**

`op` 有四种：

| op | 干什么 |
|---|---|
| `replace` | 整组替换（icon / 封面这种单张的用它） |
| `append` | 追加（截图加一张） |
| `remove` | 删掉 |
| `replace_one` | 替换其中一张，**要带 `old_value`**（从最新字段值读） |

视频不一样：`upload-video` 返回的是**数字 `videoId`**，写字段时传这个 id 而不是 URL。
而且**拿到 videoId 就算完成**，不要去轮询转码/审核状态 —— 那是服务端异步的，
不影响「字段已写入」。

⚠️ `trailer` 和 `gameplay_demo_video` **不能用同一个视频**。

---

## 四、图片大小：默认压到 4MB 以内

官方对宣传图这类字段就是限 **4MB**。手机拍/生成的图很容易超。

App 在把图收进本地暂存区时**会自动压**：先按最长边 2048 缩，再逐档降 JPEG 质量，
直到 ≤ 3.9MB（留点余量）。

如果 AI 生成素材，**明确告诉它控制在 4MB 以内**，别等上传失败才发现。

## 五、提审链路（不可逆，每一步都要确认）

```
prepare-review-snapshot   → 拿到 review_fingerprint
precheck-app-review       → 预检（不提交，只报阻塞项）
用户确认
submit-app-review --yes   → 真正提交
```

**三步必须带同一个 `review_fingerprint`**，换一个会被拒。

提交是 `high-risk-write`：**版本会进审核流，不可撤销**。
所以：
· AI **只能**做快照和预检，**真正的提交必须用户在发布页点**；
· 预检没过就不给「继续」按钮，免得用户点了才发现提交不了。

---

## 六、AI 侧怎么配合

AI 有 `taptap_publish` 工具，action 有：
`status` / `login` / `apps` / `modules` / `upload` / `save` / `submit`。

**纪律**（这些不是建议，是硬要求）：

1. **动手前先 `action=status`** —— 看缺什么，别上来就传。
2. **写操作先摊开给用户看** —— 「从什么改成什么」，拿到明确同意再执行。
3. **`action=upload` 必须传 `field`** —— 不传的话图只在素材库里，
   商店页看不到。不确定字段名就先 `action=modules` 读 `assets-upload`。
4. **`action=submit` 只能做到预检** —— 真正提交要用户在发布页点。
5. **别猜规格** —— 读 `image_spec`，不要凭记忆说「应该是 1920×1080」。

## 七、如果上传报「运输失败」

那是 **DNS 解析不了域名**，不是参数错。

原因：TapTap CLI 是个静态链接的原生二进制，它读 `/etc/resolv.conf` 做 DNS ——
而 **Android 沙箱里没有这个文件**（系统 DNS 走 netd，不是文件）。

App 的修法：起一个**本地 CONNECT 代理**，让 CLI 把请求发给它，
由 App 去解析域名（走 Android 的 resolver，正常），再开隧道转发。
TLS 是端到端的，中间看不到内容。

**如果还是失败**，按顺序查：
1. 网络本身通不通（切 WiFi / 流量试试）
2. 有没有 VPN / 代理拦着（试着全局模式或关掉）
3. 公司网 / 校园网的防火墙
