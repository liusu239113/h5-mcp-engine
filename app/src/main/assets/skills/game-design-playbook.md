# 游戏设计手册（怎么把游戏做**好玩**）

前面几份手册讲「怎么让它跑起来、不报错」。这份讲**怎么让它值得玩**。

⚠️ 最尴尬的失败不是崩溃，是「跑得好好的，但没人想玩第二遍」。
下面这些是反复验证过的判断标准，不是空话。

---

## 1. 先定「核心循环」，其余都往后放

**核心循环** = 玩家反复做的那件事。它必须满足：
**30 秒内能上手、每次重复都有变化、做完有明确反馈。**

| 游戏类型 | 核心循环 | 循环里「变」的东西 |
|---|---|---|
| 跑酷 | 跳 → 躲 → 收集 | 障碍排布 |
| 消除 | 找 → 消 → 掉落 | 新方块 |
| 塔防 | 放塔 → 打怪 → 升级 | 敌人波次 |
| 合成 | 拖 → 合 → 解锁 | 配方 |
| 文字/猜谜 | 猜 → 反馈 → 再猜 | 词库 |

**做之前先把这个循环写成一句话。** 写不出来说明还没想清楚，别开始写代码。

> 例：「玩家控制小球左右移动躲开障碍、吃金币，金币攒够就能解锁新皮肤。」
> —— 一句话里有动作（躲/吃）、有目标（解锁）、有循环（每局重复）。

---

## 2. 难度曲线：前 30 秒决定生死

新手期的标准节奏：

| 时间 | 玩家应该经历 |
|---|---|
| 0–5 秒 | **什么都不用做就能看到画面动起来**（别一上来就弹菜单） |
| 5–15 秒 | 教第一个操作 —— **用玩的教，不要用文字教** |
| 15–30 秒 | 第一次成功（吃到、消掉、过关），给一次明确的爽感 |
| 30 秒–2 分 | 难度开始爬，让他觉得「有点意思」 |
| 2 分后 | 出现失败，且**失败原因是他自己的操作**，不是运气 |

**三个反模式：**

- ❌ **一上来就是教程弹窗**。玩家是来玩的，不是来读说明的。
  正确做法：第一关只放一个障碍，他不跳就撞，撞一次就懂了。
- ❌ **难度线性上升**。人会腻。要做成「爬一段 → 松一口气 → 再爬」的锯齿。
- ❌ **随机决定生死**。玩家可以接受「我手慢了」，不能接受「我明明做对了还是死了」。

---

## 3. 反馈：每个操作都要有回应

玩家按下去之后，**200ms 内必须有可见/可听的回应**，否则他会觉得「卡了」。

| 动作 | 至少要给 |
|---|---|
| 点击按钮 | 按下缩放 0.95 + 颜色变化 |
| 吃到东西 | 音效 + 粒子 + 分数跳动 |
| 受伤 | 屏幕闪红 + 震动（`navigator.vibrate(30)`）+ 音效 |
| 失败 | 明确的原因 + 一键重来（**不要让他等 3 秒动画**） |
| 成功 | 比预期更夸张的反馈（这是「爽」的来源） |

**反馈要「过量」一点**：你觉得够了，通常还不够。玩家要的是明显。

---

## 4. 数值：给「感觉」配数字，不要反过来

**先定你想要的手感，再倒推数字。**

| 想要的手感 | 数字方向 |
|---|---|
| 轻快、跟手 | 移动速度高、加速度高、无惯性 |
| 厚重、有分量 | 加速度低、有惯性、落地有停顿 |
| 紧张 | 时间窗口短、惩罚重 |
| 放松 | 时间窗口宽、失败无惩罚 |

**参数放在文件顶部一个 CONFIG 里**，方便调：

```js
const CONFIG = {
  playerSpeed: 260,      // px/s
  jumpPower: -520,
  gravity: 1500,
  spawnGap: 1.2,         // 秒
};
```

调参靠**跑起来看**，不要靠算。用 `js_eval` 现场改数值做 A/B：

```js
// 让 AI 用 js_eval 跑这个，试不同速度的手感
CONFIG.playerSpeed = 320;
```

## 5. 关卡：手工设计前几关，之后才程序生成

- **前 3 关手工做**：它们承担教学职责，必须精确控制（第几秒出现什么）。
- **之后可以程序生成**，但要加约束：
  - 不能连续 3 个同样的障碍
  - 障碍之间的间隔必须 ≥ 玩家的反应距离（`速度 × 0.4 秒`）
  - 生成的关卡要**先验证可通过**（让 AI 自己跑一遍模拟）
- **难度用参数控制**，不要写死：`difficulty = 1 + floor(score / 500)`。

## 6. 让 AI 帮你验证「好不好玩」

这几个问题直接问自己（或让 AI 用 `js_eval` 测）：

| 问题 | 怎么测 |
|---|---|
| 一局多长？ | 跑一次，记录从开始到失败的时间。**休闲游戏 30 秒–3 分钟**最舒服 |
| 玩家平均得分？ | 模拟 20 次随机操作，看分数分布。全 0 或全满分都说明数值坏了 |
| 有没有「必死」的局面？ | 模拟里出现「怎么操作都会死」= 关卡生成有 bug |
| 卡不卡？ | 量帧时间（见 h5-handbook §3） |

```js
// 让 AI 用 js_eval 跑这个做「自动试玩」
(function(){
  let runs = [], r;
  for (let i = 0; i < 20; i++) {
    resetGame();
    let t = 0;
    while (!G.over && t < 180) { stepSim(1/60); t += 1/60; }   // 用假输入跑
    runs.push(t);
  }
  return '平均一局 ' + (runs.reduce((a,b)=>a+b,0)/runs.length).toFixed(1) + ' 秒';
})()
```

**这比你自己试玩有效得多** —— 20 局一次跑完，分布一眼就看出来了。

## 7. 手机上特有的设计约束

| 约束 | 影响 |
|---|---|
| 手指挡住屏幕 | 关键内容不要放屏幕下半部分；控制区放底部、展示区放上部 |
| 单指操作 | 别设计需要双指同时按的玩法（除非真的必须） |
| 随时被打断 | **必须能随时暂停**（`visibilitychange` 时自动暂停） |
| 没有物理按键 | 别做需要精确连招的玩法 |
| 竖屏为主 | 默认按竖屏设计；除非明确要横屏 |
| 单手玩 | 重要按钮放拇指够得到的地方（右下 / 左下） |

```js
// 切后台自动暂停 —— 手机必做
document.addEventListener('visibilitychange', () => {
  if (document.hidden) pauseGame(); 
});
```

## 8. 交付前的「好玩」自检

- [ ] 能用一句话说清核心循环
- [ ] 打开后 **5 秒内**画面动起来，**15 秒内**玩家做了第一个操作
- [ ] 每个操作 200ms 内有反馈
- [ ] 失败原因是玩家操作，不是随机
- [ ] 一局时长在 30 秒–3 分钟
- [ ] 自动试玩 20 局，分数有分布（不是全 0 / 全满）
- [ ] 切后台能自动暂停
- [ ] 关键 UI 在拇指够得到的地方、没被手指挡住
- [ ] 数值集中在 CONFIG 里，能一处调

**最后一条最重要**：如果你自己玩一遍觉得无聊，那就是无聊。别交付。
